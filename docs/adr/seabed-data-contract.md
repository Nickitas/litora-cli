# ARCH-01: контракт батиметрической модели

- Статус: принято.
- Дата: 2026-08-20.
- Версия контракта: `lito-seabed/v1`.
- Область решения: построение, проверка и экспорт рельефа морского дна.

## Контекст

Команда `lito mesh` строит двумерную четырёхугольную сетку в локальной
равновеликой проекции, но её узлы пока имеют `Z = 0`. Существующий тип
`geometry.BathymetryPoint` хранит в поле `Depth` отрицательные отметки дна.
Без отдельного контракта название `depth` допускает противоположное толкование
знака, ноль легко перепутать с отсутствием данных, а вертикальный датум —
потерять при экспорте.

Это решение фиксирует модель данных до реализации команд `lito seabed`.
Контракт распространяется на Чёрное море и локальные участки побережья.

## Принятое решение

### 1. Высота, глубина и вертикальная система отсчёта

Каноническая величина модели — `elevation_m`: высотная отметка относительно
вертикальной системы исходного набора, в метрах, с положительным направлением
вверх.

| Положение | `elevation_m` | `water_depth_m` |
|---|---:|---:|
| дно на 120 м ниже уровня отсчёта | `-120` | `120` |
| согласованная береговая граница | `0` | `0` |
| суша | `> 0`, не входит в принятую модель акватории | `0` |

Производная величина вычисляется только по формуле
`water_depth_m = max(0, -elevation_m)`. Поле `water_depth_m` положительно вниз и
предназначено для физических формул и удобного чтения. Существующее поле Go
`BathymetryPoint.Depth` до отдельной миграции интерпретируется как
`elevation_m`, то есть обязано быть неположительным.

Lito не объявляет единый вертикальный датум для всех источников. Модель
сохраняет исходную вертикальную систему без неявного преобразования. Для
каждого запуска обязательны:

- название вертикальной системы отсчёта;
- EPSG-код, если он определён источником, иначе `null`;
- единица `m` и направление `up`;
- оговорка источника о локальных или смешанных системах;
- признак и метод преобразования, если оно действительно выполнялось.

Допущение GEBCO о среднем уровне моря записывается как описание источника, но
не выдаётся за точный локальный ноль уровня для всего Чёрного моря. Назначение
`elevation_m = 0` береговым узлам является отдельным граничным условием модели
и всегда подсчитывается в отчёте.

### 2. Горизонтальные координаты

Каждый узел хранит обе системы координат:

- `longitude_deg`, `latitude_deg` — WGS 84, порядок осей явно указан как
  `longitude,latitude`, единица — градус;
- `x_m`, `y_m` — локальная сферическая азимутальная равновеликая проекция
  Ламберта (LAEA), единица — метр; центр проекции записывается в отчёт.

`x_m`, `y_m` используются для построения сетки и расчёта площадей. WGS 84
используется для выборки батиметрии и сопоставления с внешними данными.
Координата `Z` в MSH/VTU равна `elevation_m` без вертикального увеличения.
Вертикальное увеличение разрешено только как параметр визуализации.

### 3. Обязательная запись узла

Принятый узел содержит следующие поля:

| Поле | Тип и единица | Смысл |
|---|---|---|
| `id` | целое | устойчивый идентификатор, начиная с 1 |
| `x_m`, `y_m` | число, м | координаты расчётной проекции |
| `longitude_deg`, `latitude_deg` | число, ° | координаты WGS 84 |
| `elevation_m` | число ≤ 0 или `null`, м | отметка дна; `null` только для NoData |
| `water_depth_m` | число ≥ 0 или `null`, м | глубина воды по принятой формуле |
| `sampling_method` | перечисление | способ назначения значения |
| `source_distance_m` | число ≥ 0 или `null`, м | расстояние до использованной исходной точки |
| `quality_flag` | перечисление | пригодность значения |
| `is_boundary` | логический | принадлежность границе |
| `boundary_kind` | перечисление | тип границы |

`sampling_method` принимает значения `not_sampled`, `exact`, `bilinear`,
`nearest`, `irregular` или `coastline_constraint`. `not_sampled` обязателен для
NoData, чтобы не приписывать пропуску несуществующий способ интерполяции.
`quality_flag` принимает `verified`, `fallback`, `constrained`, `no_data` или
`rejected`. Тип границы: `none`, `coastline`, `island` или `open_boundary`.

Узел с `quality_flag = no_data` или `rejected` обязан иметь `null` вместо
высоты и глубины и не может входить в принятый расчётный MSH/VTU. Для прочих
узлов значения конечны и удовлетворяют формуле глубины.

### 4. Обязательная запись четырёхугольной ячейки

Принятая ячейка содержит:

- `id` и четыре уникальных `node_ids` в порядке обхода;
- `area_m2`;
- `elevation_min_m`, `elevation_max_m`, `elevation_mean_m`;
- `water_depth_mean_m`;
- `slope_deg`, `aspect_deg` (`null` для плоской ячейки), `roughness_m`;
- `region`: `coast`, `shelf`, `slope`, `basin` или `unclassified`;
- `quality_flag`: `verified`, `mixed` или `fallback`;
- `quality_score` от 0 до 1.

Метод расчёта уклона, экспозиции и шероховатости, а также пороги районов
записываются в отчёт запуска. Ячейки с NoData не экспортируются как принятые:
неполная сетка получает статус `preview_only` или `failed`.
Экспозиция задаёт направление наибольшего понижения поверхности: `0°` — север,
`90°` — восток, отсчёт по часовой стрелке.

### 5. Политика NoData и допустимость результата

NoData никогда не заменяется нулём, средним значением моря или синтетической
поверхностью без явной маркировки. В JSON и CSV используется `null`/пустое
поле вместе с `quality_flag = no_data`. В принятом MSH и VTU должны быть
покрыты 100% узлов; `NaN` и бесконечности запрещены.

Научный результат допускается только при паспорте батиметрии со статусом
`verified_derived`, совпадающей SHA-256 и описанной вертикальной системой.
Статус `synthetic_test` разрешён исключительно для тестов. Набор
`legacy_unverified_mixed` может быть прочитан для аудита старых результатов,
но новый расчёт получает статус `failed` или требует явно обозначенного
режима предварительного просмотра и не может называться научным результатом.

### 6. Распределение данных по форматам

#### Gmsh MSH 2.2 ASCII

- `$Nodes`: `X = x_m`, `Y = y_m`, `Z = elevation_m`;
- `$Elements`: четырёхугольная топология и физические группы границ;
- отдельные `$NodeData`: `elevation_m`, `water_depth_m`,
  `sampling_method_code`, `source_distance_m`, `quality_code`,
  `boundary_code`;
- отдельные `$ElementData`: средняя/минимальная/максимальная отметка,
  средняя глубина, уклон, экспозиция, шероховатость и `quality_score`.

Строковые значения кодируются целыми числами; неизменяемые таблицы кодов
`sampling_method`, `quality_flag`, `boundary_kind` и `cell_quality_flag`
дублируются в JSON-отчёте. Плоский старый MSH остаётся входом команды
`seabed build`, но нулевой `Z` в нём не считается батиметрией.

#### VTU

VTU содержит те же координаты и скалярные поля как `PointData` и `CellData`.
Это основной формат для ParaView и интерактивной 3D-проверки.

#### CSV

`nodes.csv` содержит поля записи узла в порядке, приведённом выше.
`cells.csv` содержит поля записи ячейки. Дополнительно каждый файл получает
сопутствующий JSON-отчёт с системами координат, единицами и происхождением:
CSV сам по себе не считается самодостаточным научным артефактом.

#### JSON

`seabed-quality.json` соответствует схеме
[`lito-seabed-v1.schema.json`](../schemas/lito-seabed-v1.schema.json). Он
содержит происхождение данных, системы координат, соглашения, сводку сетки,
покрытие, проверки качества, список выходных файлов и предупреждения. Полные
миллионы узлов и ячеек в отчёт не дублируются; допустим только небольшой блок
`samples` для диагностики.

### 7. Разделение ответственности CLI

`lito mesh` отвечает только за горизонтальную геометрию: береговую границу,
острова и отверстия, проекцию X–Y, топологию, размер и качество элементов.
Команда не назначает глубину и не меняет источник батиметрии.

`lito seabed build` читает готовую сетку и подтверждённую батиметрию, выполняет
обратное преобразование координат, назначает отметки, согласует береговой ноль,
рассчитывает характеристики ячеек и создаёт MSH/VTU/CSV/JSON в
`output/seabed/`. `seabed validate` только проверяет существующий результат, а
`seabed render` повторно строит визуализации без изменения численных данных.

Для адаптивной сетки модуль `seabed` может построить неизменяемое поле
желаемого размера по градиенту исходной батиметрии. `mesh` использует это поле
как вход, после чего `seabed build` заново назначает значения окончательным
узлам. Так зависимость остаётся направленной и воспроизводимой.

## Машинная проверка и синтетический пример

Схема отчёта: [`docs/schemas/lito-seabed-v1.schema.json`](../schemas/lito-seabed-v1.schema.json).
Минимальный пример одной четырёхугольной ячейки:
[`docs/examples/lito-seabed-v1.example.json`](../examples/lito-seabed-v1.example.json).
Он явно задаёт плоскость WGS 84/LAEA, отметки четырёх узлов, производные
глубины, способы выборки, границы, метрики ячейки и результат проверки.

## Последствия

- Понятия отметки и положительной глубины больше не смешиваются.
- Любой экспорт можно связать с источником, датумом, проекцией и проверками.
- Нулевой `Z` старой плоской сетки не принимается за реальное морское дно.
- Контракт добавляет служебные поля и требует 100% покрытия принятой сетки.
- Переименование Go-поля `Depth` не входит в ARCH-01 и должно выполняться
  отдельно с миграцией существующих файлов.

## Отклонённые варианты

- **Хранить только положительную глубину.** Не подходит для координаты `Z` и
  противоречит существующим данным GEBCO и Lito.
- **Считать ноль значением NoData.** Делает береговую линию неотличимой от
  пропуска данных.
- **Принудительно объявить единый MSL-датум.** Создаёт ложную точность для
  источников с разными вертикальными системами.
- **Встроить батиметрию в `mesh`.** Смешивает топологию, данные наблюдений и
  визуализацию, затрудняя повторную проверку каждого этапа.
- **Удалить старый неподтверждённый набор.** Он нужен для аудита уже полученных
  результатов; вместо удаления контракт запрещает его научное использование.
